# 纯净微博（weibo-clean）可行性分析

- 日期：2026-09-13
- 状态：可行性结论 + 初步方案，接口细节待验证（见 `docs/technical-design.md` 的验证清单）
- 相关项目：`D:\desktop\weibo`（已实现的关注列表爬取工具 weibo-follows）

## 1. 想法定义（1.0 范围）

移动端"纯净版微博"：只看到你关注的人及其相关互动，其余的（推荐内容、路人评论）一律不可见。

| 编号 | 规则 | 说明 |
|---|---|---|
| R1 | 首页信息流只显示白名单成员（= 关注 ∪ 手动添加 − 手动移除）**发布或转发**的帖子 | 广告、推荐、热搜、"TA 赞过"卡片全部隐藏 |
| R2 | 帖子评论区只显示**白名单成员**发表的一级评论 | 未在白名单的评论直接不返回 |
| R3 | 白名单成员转发的原博照常显示 | 原博作者可能不在白名单，属于"TA 转发的内容"，默认显示，可做成开关 |
| R4 | 楼中楼回复：**回复者与被回复者都在白名单**才显示 | 例：A 回复 B、C；你关注 A、B。只显示 A→B 的回复，A→C 隐藏 |
| R5 | 过滤发生在**服务端**，前端拿不到被隐藏的数据 | 不是渲染后视觉遮挡 |

明确不做（1.0，YAGNI）：发帖/转发/评论/点赞等写操作、消息通知、搜索、多账号、关注管理（可复用现有 weibo-follows 工具）。1.0 是只读客户端。

## 2. 结论

**技术可行。** 过滤本身没有算法难度（集合判断 + 评论树剪枝），真正的难点在数据来源：

1. 微博没有面向个人开发者、稳定的官方接口来做这种个性化客户端。只能带登录 Cookie 调网页版/移动版内部接口——你现有的 `weibo-follows` 项目已经验证这条路走得通（Cookie、重试、错误分类都做好了）。
2. 主要风险是：风控限流、Cookie 过期、接口随时变动、使用非官方接口违反微博服务条款。**个人自用风险低，公开发布/上架风险极高**（历史上第三方微博客户端被批量封杀）。

难度评估：

| 维度 | 难度 | 说明 |
|---|---|---|
| 工程实现（过滤、后端、前端） | 4/10 | 逻辑简单，主要是体力活 |
| 数据获取的稳定性 | 8/10 | 非官方接口 + 风控 + 接口变动 |
| 合规/法律 | 中高 | 个人自用可接受，分发不可取 |

工作量估计（一个有经验的前端/全栈，业余时间）：1.0 可用版本约 2~3 周；其中接口验证 0.5~1 天必须先做。

## 3. 关注集合完整性（M0 已验证，风险解除）

过滤的正确性依赖"我关注了谁"这份名单，名单缺人会导致评论被误隐藏。原担心 `friendships/friends` 存在约 200 条枚举上限（weibo-follows 项目曾观测到）。

M0 实测（2026-09-13，关注 263 的账号，详见 `fixtures/m0-findings.md`）：

1. 评论/帖子/流数据里的用户对象**自带 `following` 布尔标记**（我是否关注 TA），可逐条判断，完全不依赖全量名单；
2. 关注名单有两条可翻到底的路径：`profile/followContent`（50/页）与 `friendships/friends`（20/页，实测可达第 14 页 258 条），未复现 200 硬上限；
3. 兜底：`profile/info?uid=` 可单条查询关系；
4. 少量用户受平台 `has_filtered_attentions` 过滤无法枚举（差 5~9 人属正常），不影响主线。

## 4. 实现方式对比

| 方案 | 形态 | 开发成本 | 移动端体验 | 能否保证"前端拿不到脏数据" | 维护成本 |
|---|---|---|---|---|---|
| **A（推荐）自托管 Web 应用 + PWA** | 电脑/VPS 跑服务，手机浏览器访问 | 中 | 好 | 能（服务端过滤） | 中 |
| B 油猴脚本改造 m.weibo.cn | 手机浏览器装脚本 | 低 | 取决于浏览器（iOS 差） | 基本能（拦截 XHR 响应再注入） | 高（微博改版即失效） |
| C 安卓 WebView 壳 | 自写 App 加载 m.weibo.cn + 注入过滤 | 中高 | 好（仅安卓） | 基本能 | 高 |

**推荐 A**，理由：

- 服务端过滤是唯一能对 R5 做出保证的方式；油猴/WebView 方案本质是"在客户端改数据"，脚本失效时可能退化成"脏数据短暂可见"。
- Cookie 只存在你自己的机器上，不经过任何第三方。
- 后端天然做缓存，能显著降低对微博接口的请求量（降低风控风险）。
- 未来如果想做原生 App，后端 API 可以直接复用。

方案 B 适合作为"先尝一口"的快速原型；方案 C 如果最终想要 App 图标和推送体验再考虑。

## 5. 推荐架构（方案 A，已确认）

```
手机浏览器 (PWA)
   │  HTTPS/局域网
   ▼
自托管后端 (FastAPI + SQLite)
   ├─ 微博接口客户端：Cookie、限速、重试、错误分类（复用 weibo-follows 的经验）
   ├─ 关注名单同步：定时/手动，缓存到本地库
   ├─ 原始数据缓存：帖子、评论原样落库（TTL），避免重复抓取
   ├─ 过滤引擎：纯函数，输入"评论树 + 关注集合"，输出可见树（可单测）
   └─ REST API
   ▼
微博内部接口 (weibo.com / m.weibo.cn，带你的 Cookie)
```

- 前端建议：React/Vue + Vite 的移动端 PWA；页面少，只有三个：关注流、帖子详情（正文 + 过滤后的评论树）、设置（Cookie、同步、开关）。
- 部署：先在电脑上跑（手机同 Wi-Fi 或 Tailscale 访问）。注意 PWA 的"添加到主屏幕"完整能力需要 HTTPS，局域网 IP 不行；Tailscale 可以提供证书，或后续用方案 C 的壳解决。
- 数据只在本地：SQLite 单文件，随时可删。

## 6. 过滤引擎要点（核心逻辑，简单）

对每条评论做"作者是否在关注集合中"的判断，再对回复做"双方都在集合中"的配对判断，然后剪枝：

```
可见性(node)：
  1. 作者 ∈ 关注集合，否则隐藏
  2. 若 node 是回复（有被回复对象）：
       被回复者 ∈ 关注集合，否则隐藏
  3. 递归处理子回复
```

实际落地需要处理的边界（详见技术方案文档）：

- 被回复者 uid 的获取：优先接口的 `reply_comment` 字段；否则从评论 HTML 里的 `@昵称` 链接 href 中解析 uid；再否则用昵称与关注名单比对。
- 孤儿回复：A→B 的回复合法（双方都关注），但它挂在"B 回复了 C"这条被隐藏的评论下面。默认策略是把该回复**提升到可见层级并标注"回复 @B（上下文已隐藏）"**，而不是连带隐藏。
- 转发的展示：卡片作者必须是关注的人；卡片内引用的原博与原作者照常显示（R3）。
- 点赞：微博不公开"谁点了赞"，这部分天然没有可过滤的数据。

## 6.5 Demo 运行说明（本地）

白名单（v0.2 新增）：

- 默认白名单 = 你的关注；无需同步，关注变化自动生效。
- 顶栏"白名单"进入管理页：粘贴主页链接/UID 添加未关注的人（其原创帖会并入信息流）；对关注中的人点"隐藏"可移除；"已隐藏"里可恢复。
- 你自己始终可见（自己发的帖子、评论、回复都会显示，不参与过滤）。
- 数据只存在本地 `whitelist.json`（已 gitignore），可随时删除重置。

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
# 确保项目根目录存在 cookie.txt（从浏览器复制，格式同 weibo-follows）
.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

- 电脑访问 `http://127.0.0.1:8000`；手机与电脑同一 Wi-Fi 时访问 `http://<电脑IP>:8000`。
- 测试：`.venv\Scripts\python.exe -m pytest -v`
- Demo 已知限制：只读；只加载关注流最新一页；评论/回复最多抓取前 3 页（每页由微博决定，约 2~5 条），回复按楼懒加载；无数据库/PWA；手动添加的人越多刷新越慢（每人一次抓取，缓存 10 分钟）；评论过滤依赖本地关注名单（10 分钟缓存），首次打开详情可能多等几秒。

实现计划见 `docs/superpowers/plans/2026-09-13-weibo-clean-demo.md`。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 风控限流/封号 | 服务不可用 | 低频只读、请求随机延时、结果缓存、失败明确提示不重试风暴 |
| Cookie 过期 | 服务不可用 | 启动时检测，设置页一键更新，失效时明确引导（复用现有错误分类） |
| 接口变动 | 功能失效 | 微博调用全部收敛在 client 层，单点修改；保存 fixtures 便于回归 |
| 关注集合残缺 | 评论误隐藏 | 已缓解：`following` 标记直出 + 双路径枚举；少量平台过滤用户无法枚举，属正常 |
| 服务条款/法律 | 个人可用，分发危险 | 仅个人自用、不公开分发、不盈利、数据不外传；阅读微博服务条款并知悉风险 |
| PWA 需要 HTTPS | 手机安装体验受限 | Tailscale/自签证书，或接受普通网页访问 |

## 9. 与现有 weibo/ 项目的关系

- 复用：`WeiboClient` 的 Cookie/重试/错误分类模式（退出码 1/2/3 的约定）、`FollowedUser` 模型与导出格式。
- 扩展：关注名单的完整获取（200 条上限的绕过调研）是 M0 的一部分。
- 新项目独立成目录（本项目 `weibo-clean`），不要改动原工具；后端可直接把原工具的关注列表导出作为初始名单导入。
