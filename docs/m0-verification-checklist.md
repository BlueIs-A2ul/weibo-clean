## 0. 目标与判定逻辑

验证两件事，它们决定整个项目的实现路径：

1. **数据是否拿得到**：关注流、帖子、评论树（含楼中楼）的内部接口是否可用、结构是否稳定。
2. **过滤依据是否可靠**：能不能判断"我是否关注某用户"——要么评论数据自带关系标记，要么关注名单能完整同步。

所有任务中的接口形态都是**预期**，一切以你实际抓到的请求为准。抓到就记录，抓不到记"失败"，不要自己造。

## 1. 准备

- [ ] Chrome/Edge 桌面版，已登录微博（用你日常使用、真正要过滤的那个账号）
- [ ] 备份一份当前 Cookie 到 `cookie.txt`（沿用 weibo-follows 的用法；文件不进 Git）
- [ ] 新建目录 `D:\desktop\weibo-clean\fixtures\`
- [ ] 复制 `m0-findings-template.md` 为 `m0-findings.md`，边做边填
- [ ] DevTools：F12 → 网络 → 筛选器选 `Fetch/XHR` → 勾选"保留日志"

安全与频率原则：

- 全程只做"看"的操作（滚动、点开帖子、展开评论）。**不要关注/取关/点赞/评论**，否则会改变你需要观测的证据。
- 请求频率保持人类速度（几秒一次），和平时刷微博一致；出现风控提示（页面报错/接口返回异常 code）就停下，半小时后再试。
- 保存响应时用"右键 → 复制响应"贴进文件；**不要保存 HAR**（HAR 会包含 Cookie）。
- fixtures 里可能有其他用户的评论内容，仅本地留存，不公开、不提交到任何公开仓库。

## 2. V1：关注流接口

目的：确定首页"关注"时间线的请求、分页方式、卡片结构、广告标记。

- [ ] 打开 `https://weibo.com/`，清空网络面板，滚动首页触发 2~3 次加载
- [ ] 在网络面板里找返回帖子列表的请求（名称通常含 `following` / `feed` / `home`，以实际为准）
- [ ] 点击请求 → 响应，记录以下内容：
  - [ ] 完整 URL（含 query 参数名）
  - [ ] 分页参数与响应中的游标字段（如 `since_id` / `max_id` / `page`）
  - [ ] 帖子数组在 JSON 中的路径（如 `data.list`）
  - [ ] 单条帖子的关键字段：`id`/`mid`、`user.id`、`text`、配图字段
  - [ ] 转发帖：原博嵌套在哪个字段（如 `retweeted_status`），转发者是谁
  - [ ] 广告/推荐卡片长什么样：`is_ad` / `promoted_content` / `card_type` 等标记字段名
- [ ] 对照 m 站：打开 `https://m.weibo.cn/`，切到"关注"tab 再抓一次（结构通常更简单，可能作为客户端主接口）

通过标准：能连续拿到至少 3 页关注流，每页都有可识别的作者 uid，且记录到广告标记字段。

卡住时：改用"某个用户主页"的时间线接口验证内容结构（如 `ajax/statuses/mymblog`），关注流单独再找。

记录到 findings：V1。

## 3. V2：帖子详情

目的：确定单条帖子的接口，供详情页和评论页使用。

- [ ] 在首页点开一条帖子（或右键"在新标签打开"，保持网络面板记录）
- [ ] 找到返回帖子详情的请求，记录 URL、`id` 参数形态（mid）、响应里正文/作者/互动数字段
- [ ] 特别确认：详情响应里作者 `user` 对象有没有 `following`、`follow_me` 字段

通过标准：一条帖子的完整结构可获取。

记录到 findings：V2。

## 4. V3：一级评论

目的：确定评论列表接口、分页方式、每条评论的结构。

- [ ] 在帖子详情页展开评论区，滚到底触发"加载更多"
- [ ] 找到评论接口，记录：
  - [ ] URL 与参数（`id`/`mid`、`count`、`fetch_level` 或 m 站的 `max_id`/`max_id_type`）
  - [ ] 评论数组路径、分页游标字段
  - [ ] 单条评论字段：`id`、`user.id`、`text`（HTML 还是纯文本）、`like_count`、`total_number`（回复数）
  - [ ] 响应里的 `total_number`（评论总数）
- [ ] 找一个你**已关注**和一个你**未关注**的评论者，各复制其 `user` 对象字段清单（V5 要用）

通过标准：能翻页拿到一级评论，且能拿到每条评论的作者 uid。

记录到 findings：V3。

## 5. V4：楼中楼与"被回复者"

目的：确定回复怎么展开、能否拿到被回复者的 uid（R4 配对的依据）。

- [ ] 找一条有回复的评论，点"展开更多回复"/"查看全部回复"
- [ ] 记录：
  - [ ] 楼中楼接口 URL、参数（父评论 id、分页）
  - [ ] 回复条目里表示"被回复对象"的字段，例如 `reply_comment`、`reply.user.id`、`reply.text`
  - [ ] 回复层级结构：是两层扁平化（文本带"回复@昵称:"前缀），还是真正的树
  - [ ] 文本里 `@昵称` 是不是 HTML 锚点，href 里有没有 uid（形如 `/u/1234567890`）
- [ ] 分别对一个"已关注"和一个"未关注"的被回复者样本记录字段名

通过标准：每条可见回复都能确定"谁回复了谁"，至少有 2 种解析路径中的 1 种可用（字段直出 或 HTML 锚点解析）。

记录到 findings：V4。

## 6. V5：关系标记 following（最高优先级）

目的：确认评论作者对象里是否自带"当前登录者是否关注 TA"。如果有，项目可以彻底绕开"关注名单 200 条上限"问题。

- [ ] 在 V2/V3/V4 已保存的响应里，Ctrl+F 搜索 `following`、`follow_me`
- [ ] 对比样本：抽 5 个你已关注 + 5 个你未关注的用户
  - [ ] 逐条对照 `following` 字段的 true/false 是否与事实一致
  - [ ] 注意区分 `following`（我关注 TA）和 `follow_me`（TA 关注我），不要弄混
- [ ] 如果评论接口没有，再检查：帖子详情接口、用户主页接口（打开非关注用户主页时的 XHR）

通过标准：10 个样本判定 10/10 准确。只要有一个稳定的接口返回该标记，V7 可跳过。

记录到 findings：V5。

## 7. V6：关注名单枚举上限（最高优先级）

目的：确认现有工具踩到的"约 200 条上限"是否绝对，寻找绕过路径。

- [ ] 找一个关注数 300+ 的账号（可先用你的账号；不够就用你认识的大 V）
- [ ] 浏览器直接访问（已登录状态）：
  `https://weibo.com/ajax/friendships/friends?uid=<该账号uid>&page=11`，以及 `page=15`、`page=20`
  - [ ] 记录每页 `users` 数组长度与响应里的 `ok` / `total_number`
- [ ] 用现有工具跑一次该 uid，记录实际枚举数 vs `total_number`
- [ ] 替代路径（按优先级，各限时 20 分钟）：
  - [ ] m 站"我的关注"页：打开 `https://m.weibo.cn/p/index?containerid=231093_-_selffollowed`，翻到底，找列表请求，记录 containerid 与能翻到的最大页
  - [ ] 关注分组：看"关注分组/分组管理"页有没有成员列表接口，翻页上限多少
  - [ ] 官方开放平台：登录 `open.weibo.com`，看能否申请网站接入 App 与 `friendships` 读权限（只做可行性判断，不提交审核）

通过标准：至少一条路径能对 300+ 关注账号拿到与 `total_number` 一致的 uid 集合；或确认不存在这样的路径（记录为失败，走 V7 兜底）。

记录到 findings：V6。

## 8. V7：单条关系查询兜底（仅当 V5 失败时做）

目的：找不到 `following` 标记时，退而求其次——逐人查询"我是否关注 TA"，本地缓存。

- [ ] 打开一个你**未关注**的用户主页，Network 面板保持记录，观察页面加载后是否有任何请求的响应里包含该用户的 uid 和关系状态
- [ ] 再打开一个你**已关注**的用户主页，重复一次，对比
- [ ] 候选：用户主页信息接口（如 `ajax/profile/info?uid=`）、用户悬浮卡片接口、粉丝/关注列表条目里的关系字段
- [ ] 记录：接口 URL、响应中的关系字段名与取值

通过标准：存在一个低成本的接口能判断任意 uid 的关注关系。

卡住时：记录失败即可。最坏降级方案是"只显示已同步名单内的用户评论，UI 标注可能漏显"，demo 仍然可做。

记录到 findings：V7。

## 9. 结果判定矩阵

| V5 关系标记 | V6 名单完整 | 实现路径 | Demo 预计 |
|---|---|---|---|
| 有 | 无所谓 | 最佳：评论逐条判关系，无需全量名单 | 1~2 天 |
| 无 | 完整 | 同步名单后本地集合判断 | 1~2 天 |
| 无 | 残缺 | V7 逐人查询 + 缓存 + 限流 | 2~3 天 |
| 无 | 均失败 | 降级：名单内可见 + 标注"可能漏显" | 仍可做，但体验打折 |
